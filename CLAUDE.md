# CLAUDE.md — Quiz App

## Стек
- Vite + TypeScript + React
- `react-quiz-kit` — headless/hooks-слой состояния квиза
- `react-markdown` + синтаксическая подсветка — рендеринг вопросов с кодом
- **Mantine** — UI-компоненты (CSS Modules, без CSS-in-JS)
- **TanStack Router** — навигация между страницами
- **Playwright** — E2E-тесты в браузере

## Команды
```bash
npm run dev      # dev-сервер
npm run build    # production-сборка
npm run lint     # линтер
npm run knip     # проверка на мёртвый код
npm run test     # unit-тесты
npm run e2e      # E2E-тесты (Playwright)
```

## E2E-тесты (Playwright)
- Тесты размещаются в `e2e/` в корне проекта.
- Покрывать ключевые пользовательские сценарии: старт квиза, прохождение вопросов, финиш, страница результатов, статистика.
- Перед коммитом фичи, затрагивающей UI-поток, убедиться что `npm run e2e` проходит без ошибок.
- Тесты пишутся на Playwright Test (`@playwright/test`). Использовать `page.goto`, `page.click`, `page.locator`, `expect`.

### Селекторы и data-testid

Приоритет выбора селектора (от предпочтительного к запасному):
1. `getByRole` + `name` — для кнопок с текстом, заголовков, инпутов с лейблом.
2. `getByTestId` — для элементов без явной семантики или там где `getByRole`/`getByText` ненадёжны.
3. `getByText` с `{ exact: true }` — только если нет `data-testid` и роль не применима.

**Правило:** при добавлении нового интерактивного элемента, который не имеет уникальной текстовой роли (иконочные кнопки, сегменты фильтра, карточки), **сразу** проставлять `data-testid`.

Формат атрибутов:
```
// Элементы без динамического контекста
data-testid="filter-all"
data-testid="quiz-download"

// Элементы в списке (с идентификатором сущности)
data-testid="quiz-card-js-basics"
data-testid="quiz-download-js-basics"
data-testid="quiz-delete-js-basics"

// Секции/контейнеры
data-testid="results-filter"
data-testid="question-card-0"
```

## Архитектура — FSD
Проект следует Feature-Sliced Design. Подробнее: @docs/architecture.md

Ключевые правила:
- Импорты только из слоёв **ниже** своего. Слайсы одного слоя не импортируют друг друга.
- Каждый слайс экспортирует только через `index.ts` (публичный API).
- Алиас `@/` = `src/`. Использовать везде вместо относительных путей.
- `react-quiz-kit` отвечает только за состояние. Вся бизнес-логика reveal и скоринга — в нашем коде.
- Не добавлять функциональность сверх запроса. Не мокировать данные там, где ожидается реальная логика.

## Качество кода

### Автоматические проверки (pre-commit)
При каждом `git commit` автоматически запускается `lint-staged` — ESLint на staged `.ts`/`.tsx` файлах с флагом `--max-warnings=0`. Коммит будет заблокирован при наличии ошибок или предупреждений.

### Ручные проверки
- `npm run knip` — детекция мёртвого кода (неиспользуемые файлы, экспорты, зависимости). Запускать при рефакторинге, удалении файлов, изменении публичного API слайсов.
- `npm run lint` — полная проверка всего проекта (не только staged).
- TypeScript (`noUnusedLocals`, `noUnusedParameters`) — включён в `tsconfig.app.json`, `tsc` ловит неиспользуемые переменные на уровне компилятора.

### Правила
- При добавлении нового файла/модуля убедиться что он импортируется — иначе `npm run knip` его поймает.
- Не оставлять неиспользуемые экспорты в `index.ts` слайсов.

## Git
- Коммит после каждой логически завершённой единицы работы (фича, фикс, рефактор).
- Сообщения коммитов в формате Conventional Commits: `feat:`, `fix:`, `refactor:`, `chore:`, `docs:`.
- Коммитить только связанные изменения — не смешивать несколько несвязанных правок в одном коммите.
- Не коммитить сгенерированные файлы, артефакты сборки и `.env`.
- Ветки для фич: `feat/<название>`, для фиксов: `fix/<название>`.

## Порядок разработки (спринты)
1. UI-скелет + модель вопросов + базовая навигация. Без reveal и таймера.
2. Таймер + прогресс/очки + переход на Results.
3. Reveal правильных/неправильных + скоринг multi/single.
4. Статистика (localStorage) + UX reveal/exit.

## Планирование фич
Фичи хранятся в `docs/features/planned/` и `docs/features/done/`.
- Новая фича → создать `docs/features/planned/<slug>.md`, добавить в индекс.
- Взята в разработку → статус `in progress` внутри файла, создать ветку `feat/<slug>`.
- Завершена → переместить файл из `planned/` в `done/`, обновить индекс.
- Индекс всех фич: `docs/features/README.md`.

## Лог решений
После каждого ревью кода, значимого архитектурного решения или отклонённого замечания — фиксировать в `docs/log.md`:
- что найдено / решено / отклонено
- почему (обоснование)

Формат записи: `## YYYY-MM-DD — <тема>` с кратким описанием.
